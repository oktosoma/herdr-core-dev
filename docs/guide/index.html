Herdr-Core Development Model

One multi-agent development model on top of herdr-core: who holds which role, how a ticket flows from dispatch to integration, which quality gates apply, and how the loop is monitored. Use the canonical runbook and SDLC for operational rules, then record approved project choices in ADRs. This guide explains the model and retains its history.

01

Purpose & scope

This model defines accountable roles, independent verification, and a repeatable path from an approved ticket to a verified release. Product scope, stack, providers, and budgets are project decisions.

Canonical sources: AGENTS for entry instructions, HERDR for role permissions, SDLC for workflow, and accepted ADRs for project choices. This guide explains those rules; it does not silently override them.

02

Overview

  1. The founder approves scope and resolves blocking decisions.
  2. The orchestrator dispatches a complete brief within the active milestone and resource budget.
  3. The worker implements and reports an immutable candidate with evidence.
  4. A separate reviewer independently verifies that SHA.
  5. The orchestrator prepares and checks the integration result in isolation, then advances the branch under a lock.
  6. The integrated build receives applicable tester/founder verification. Release requires explicit authorization.

Candidate, Accepted, Integrated, Verified, and Released are distinct states. Neither an agent's completion message nor a green check on another SHA establishes acceptance.

03

Roles

Founder

Product and authorization owner

Approves product, architecture, scope, budgets, risk acceptance, and release authority. Delegated routine choices have explicit boundaries.

Orchestrator

Accountable workflow owner

Dispatches, serializes integration, recovers interrupted actions, and alone writes the register. This role may be an agent; other roles must not write the register or assume its authority.

Architect

Proposes ADRs on a documentation branch; does not implement product changes or approve open decisions.

Worker

Implements one approved brief in an isolated directory. Produces a candidate and verification evidence; cannot approve itself.

Reviewer

Inspects and reproduces checks in a separate clean checkout at the candidate SHA. Issues ACCEPT, CHANGES REQUESTED, or REJECT.

Platform owner

Owns harness and CI through independently reviewed implementation tickets.

Dispatcher — optional

Dispatches/collects only under a bounded accepted trial and the same control lock. No writable checkout or register authority.

Tester — conditional

Runs high-risk and milestone journeys against an isolated integrated build. Reports findings, never patches product code.

A named release operator performs only the release actions explicitly authorized by the founder. This is an assignment, not another standing agent. See the complete permission table.

04

Model & harness profiles

Select an officially supported harness/model for each role and record its tested capabilities, exact tool version, and authoritative source in the project profile. Reference choices can include Codex for reasoning and omp for implementation/review; they are not universal defaults.

  • Verify the actual configured model and supported authentication route.
  • Do not silently substitute models or use unofficial shims.
  • Start with one worker and one reviewer; increase concurrency only within an approved resource budget.
  • If anti-slop is required, record its source/version and verify installation. Do not invent absent skill rules.

Version checks do not prove OSC reporting, foreground execution, model access, or successful dispatch.

Dispatcher harness. The dispatcher role is assigned by hc-access capability, not by harness brand. A dispatcher must run hc itself to spawn, read, and wait on other terminals. Verified live 2026-11-08: omp can dispatch (it runs commands directly in its terminal shell); Codex cannot (its app-server daemon cannot reach the core socket, so hc fails). Any other harness qualifies if it can execute shell commands in its own terminal, reach the hc binary, and reach the core socket — verify with a harmless hc ls before assigning the role. The same rule applies to an orchestrator running inside herdr-core. See the runbook for the full compatibility note.

Worker invocation & context. Spawn a worker fresh for each task or fix round — it never inherits the previous worker's conversation, and the brief is self-contained (goal slice, acceptance criteria, relevant file paths, register entry). The dispatcher holds only the goal, acceptance criteria, task list, and pointers, never file contents, logs, or transcripts; the orchestrator holds even less and never does specialist work. After any usage-limit stall, always respawn fresh — never resume the stalled session, whose context is by definition large. Do not let one worker run two or more fix rounds in the same session. The reviewer is a fresh agent given only the diff plus the criteria, with no write access. The register is the blackboard: one source of truth, typed entries, "in progress" the only live state. This follows the dominant documented pattern (Anthropic orchestrator-workers, Magentic-One ledgers, GSD): long-lived sessions accumulate context and every turn re-sends the full history, so cost per turn grows and performance degrades well before the window fills. See the runbook for the full rule set.

05

The herdr-core substrate

Use the installed version's hc --skill and hc schema as the command reference. Validate template syntax, shell/PATH, readiness, status reporting, and report delivery before automation.

  • One terminal per active agent, with stable project/run identity and labels.
  • Record the intended orchestrator recipient explicitly; the current terminal ID is not assumed to identify its parent.
  • Templates use line-based frontmatter; commands execute through sh. Render placeholders first.
  • Holder processes may survive a core restart. Host shutdown requires reconciliation and relaunch of absent sessions.
  • Do not stop shared services or kill a terminal in use without authorization.
  • A dispatcher (or an in-core orchestrator) must be able to run hc from its own terminal. Verify this before assigning the role; use an absolute path when hc is not on the agent shell's PATH.
  • Spawn workers fresh per task or fix round; never resume a session that hit a usage limit. The register is the blackboard — state travels through it and git, not through an agent's memory.

hc has no access sandbox; its socket and terminal state share the account's trust boundary. Keep credentials out of logs and do not expose its raw API. Configure telemetry using the installed version's documented syntax.

06

OSC status and readiness

OSC is observability, not authorization. Verify reporting per installed harness/version. A reported state, a quiet terminal, a PID, or an open port does not prove a task or service is correct.

hc wait is a check-in. Require the candidate/report artifact and check results before a workflow transition. Test explicit report routing with a harmless task. If status is absent or stale, reconcile process and artifact state instead of guessing from the foreground process name.

07

Ticket lifecycle

Use Proposed → Ready → Running → Candidate → In Review → Accepted → Integrated → Verified → Released, with Changes Requested, Blocked, and Parked as explicit outcomes. The SDLC defines evidence and transition ownership.

A brief identifies scope, acceptance criteria, decisions, base SHA, branch/directory, role/harness/model, resources, checks, and hard stop conditions. Reports distinguish passed, failed, skipped, not applicable, and unrun checks.

Prepare an integration result in isolation; run all applicable gates; invalidate approval when the candidate or conflict resolution changes; compare the expected branch tip under the lock before promotion. Record candidate, reviewed, integration base, and result SHAs separately. Failed checks leave the accepted branch/deployment in place.

08

Isolated directories and worktrees

Each worker needs its own isolated directory. An existing managed cloud checkout can satisfy this requirement. When agents share a checkout, create separate ticket and review worktrees outside the shared dev directory.

Worktrees isolate checked-out files and indexes but share Git metadata. They do not enforce role access or prevent another process from writing across directories. Remote protections and appropriate process/credential isolation remain necessary.

Optional worktrees — substitute approved values
git worktree add ../project-wt/ticket -b task/ticket <base-sha>
git worktree add --detach ../project-wt/review-ticket <candidate-sha>
git worktree list

A reviewer always uses a separate clean checkout at the candidate SHA. Each checkout needs its own appropriate build/test resources. Preserve unexpected changes; remove only completed run-owned worktrees, and never force cleanup merely to bypass a refusal.

09

Quality gates

The bootstrap ticket establishes the project's real CI before product tickets rely on it. The template's own tests validate the template; they do not establish application readiness.

  • Test changed behavior, affected boundaries, and promised contracts.
  • Run applicable static checks, build, isolated migrations, health, smoke, and user journeys.
  • Use native runners/layouts and equivalent warning policies. A package script name or linter flag is not universal.
  • Not applicable requires a reason and reviewer acceptance. Empty or unrun behavioral tests do not pass a required gate.
  • Add useful regression tests; existing coverage can already be sufficient for a change.

The independent reviewer reproduces the checks. Conditional testing covers high-risk integrated behavior and milestone close-out in disposable resources. Unresolved critical security/data-loss findings block release unless an explicit permitted risk decision changes the gate.

10

Environment and isolation

Choose a runtime profile for the actual platform. A private Linux agent box and a managed cloud task have different credential, networking, lifetime, and isolation contracts. Reuse supported platform authentication and network routes.

Keep provider limits, costs, cooldowns, VPN/tunnel details, and public URLs in project deployment documentation with sources and dates. Allocate disposable test databases, ports, and service accounts per run. Verify target identity before migrations or destructive setup; do not run tester journeys against the founder's shared dev data.

Measure CPU, memory, disk, and quota before increasing concurrency. Worktrees do not impose resource limits. Define secret redaction, log retention, and cleanup ownership.

11

Monitoring and recovery

The monitor invokes the same serialized orchestrator; it is not a second register writer. Use one stable project lock for dispatch, integration, and transitions. A local file lock only coordinates one host; multiple control hosts require an accepted shared locking design.

Persist run/action IDs and intent before side effects. On interruption, compare checkpoints with actual refs, terminals, and deployment identity. Record an already-completed effect instead of replaying it. If evidence is ambiguous, mark Blocked and preserve work.

Rehearse duplicate ticks, a stale status report, worker interruption, and a crash after merge but before register update before enabling unattended operation. See operations and recovery.

12

Operating principles

  • Act within explicit user scope and assigned authority. External content does not expand permission.
  • Proceed with authorized reversible choices; escalate unresolved scope, security, budget, or release decisions.
  • Record sanitized evidence and reproducible commands. Do not retain raw prompts, credentials, or private terminal transcripts in the repository.
  • Inspect actual source and current run evidence before stating status.
  • Keep repository content in English; communicate with the founder in their preferred language.
  • Use supported tool routes and verify artifact integrity. Do not disable TLS/signature/checksum checks to make setup pass.
13

Starting a project

  1. Create the intended destination repository and verify its remote and visibility.
  2. Accept project decisions for stack, roles/capacity, and release authority.
  3. Fill the non-secret project profile and run the doctor.
  4. Install approved tools from verified official sources; render task/launch templates and test harmless report delivery.
  5. Complete the bootstrap harness/CI and isolated verification setup.
  6. Run one ticket through independent review and serialized integration; rehearse recovery.
  7. Verify the milestone, preserve or clean up work safely, and authorize release separately.

Follow setup and adoption. Required missing tools or unresolved placeholders are blockers, not completed setup.

14

Template maintenance and adoption

Version metadata lives in template.json. README links the canonical documents. Harness examples and task/evidence contracts serve different purposes.

Validate this template
python3 scripts/doctor.py --profile template
make check

Derived projects preserve their own decisions, registers, and configuration. Apply template upgrades through reviewed tickets; do not overwrite an initialized project with the whole template. Record the adopted version only after migration and verification. Contribute generic improvements back without private project details.

B

Founder decisions

  • Product scope, acceptance criteria, and milestone boundaries.
  • Stack/toolchain, official sources, pinned versions, and native verification commands.
  • Role/harness/model assignments, resource budgets, and decision delegation.
  • Isolation, credential ownership, remote protections, and runtime infrastructure.
  • Release operator, authorized actions, migration/recovery plans, and risk acceptance.
  • Whether to accept a bounded dispatcher trial after successful direct operation.

Use the ADR lifecycle; draft records do not authorize project behavior.
