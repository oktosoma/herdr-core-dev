Herdr-Core Development Model

One multi-agent development model on top of herdr-core: who holds which role, how a ticket flows from dispatch to integration, which quality gates apply, and how the loop is monitored. Compiled from a live loop that already ran end-to-end — with no project-specific details, so a new project can simply follow this model.

01

Purpose & scope

What this guide exists for — and what it deliberately does not govern.

This guide defines one multi-agent development model on top of herdr-core: who holds which role, how a ticket flows from dispatch to integration, which quality gates apply, and how the loop is monitored. One project = one application of this model.

If the model changes, record the change as a dated entry in the Versions section at the end of this guide — never silently edit a rule that is currently in force.

Not part of this guide

The project stack (language, framework, database), product content, pricing / billing, and provider identity. All of those are founder decisions, made per project — this model governs only how the work is done, not what is built.

02

Overview

Seven actors, one substrate, one ticket flow.

The substrate: herdr-core (hc) on a single Linux agent box. Git as the source of truth (register, ADRs, branches). A cron monitor as the heartbeat of the loop.

One ticket, in brief

Step 1Founder sets the ticket

Ticket + acceptance criteria are set; open questions are decided by the founder.→

Step 2Orchestrator dispatches

A complete brief to the worker — its own worktree + branch per ticket.→

Step 3Worker implements

Code + tests in its worktree, then reports DONE with a candidate commit.→

Step 4Reviewer verifies

Independently, from a separate checkout — re-running the checks, not trusting the transcript.→

Step 5Orchestrator integrates

Merge into the integration branch, re-verify, update the register.→

Step 6Next ticket

The loop continues until the milestone is done; the cron monitor keeps the heartbeat.

The separation principle underneath everything

The one who decides (founder), the one who runs the loop (orchestrator), the one who does the work (worker), and the one who verifies (reviewer) are different parties. No agent ever both produces and approves its own work.

03

Roles

Responsibilities and hard limits for every role. The limits are not advice — they are part of the model.

Founder

Product owner · human

Decides everything that is open (architecture, product, billing, identity, infrastructure), tests dev, holds credentials via the vault, and approves dispatch across milestones. The only party allowed to make an open decision.

Orchestrator

Any harness with a strong reasoning model

Runs the loop: dispatches, integrates, reports, and recovers. The single merger into the integration branch. The role is not tied to any one harness — what qualifies a harness for it is a strong reasoning model behind it (reference: Codex with GPT-6.1-SOL; Muse also qualifies). Pick whichever qualifying harness is available; the role's limits stay the same. The orchestrator can also run inside herdr-core itself, as one of its own terminals — it does not have to sit outside the core.

Hard limits
  • The only writer of the register — never delegates register writing
  • Never makes an open decision
  • Never merges into main
  • Never dispatches beyond the milestone currently in progress

Architect

Codex · GPT-6.1-SOL

Advisory. Answers hard architecture questions; recommendations are written up as ADRs. Never touches an implementation branch.

Hard limits
  • Never holds /goal
  • Never writes the register
  • Never changes code

Dispatcher

Codex · GPT-6.1-SOL · core phase, optional

One pane in the core that holds /goal per ticket (acceptance + a hard stop clause). Dispatch + collect only.

Hard limits
  • No architecture decisions; no register writes
  • No writable worktree — reads the integration branch / main only
  • All escalations go to the orchestrator
  • Kill switch: the orchestrator takes over driving directly

Worker

omp · Terra / Luna

Implements one ticket in its own worktree + branch: writes code + tests, then reports DONE with a candidate commit + evidence.

Hard limits
  • One ticket per agent; never writes the register
  • Never touches the dev / prod database — verification uses a disposable DB

Reviewer

omp · GPT-6.1-Terra · single

Verifies a candidate independently from a separate checkout. Independent reproduction is mandatory. Verdict: ACCEPT / CHANGES REQUESTED / REJECT, with reasons.

Hard limits
  • One reviewer at a time (single-reviewer discipline)
  • Never decides an open question — asks for an explicit founder decision

Platform Owner

omp · as assigned

Owns the test harness + CI as the milestone gate, plus follow-up automation once the gate passes. One owner for harness + CI — never split.

A note on the dispatcher

The dispatcher is a core-phase pattern. Its trial is limited: it starts only after the first ticket has been integrated in the core with the orchestrator driving directly via hc. Until the trial is proven, the orchestrator drives directly.

04

Model & harness policy

The reference role → harness → model mapping, plus the rules that go with it.

NeedHarnessModel
Orchestrator (loop control, judgment calls)Any harness — the requirement is a strong reasoning modelReference: GPT-6.1-SOL
Architect, dispatcher, other reasoningCodexGPT-6.1-SOL
Workers that need minimal hallucination; the reviewerompGPT-6.1-Terra
Light / fast workompGPT-6-Luna

The selection logic: reasoning and judgment (architecture, dispatch, review) get the strongest model or the one with the lowest hallucination rate; light-volume work is absorbed by the fast model so the flagship quota lasts. The reviewer is deliberately not a light model — a careless verdict is the most expensive failure in this loop.

Rules that go with it

  • The orchestrator role is harness-agnostic. It does not have to be Muse or any other specific harness — the requirement is a harness running a strong reasoning model (reference: Codex + GPT-6.1-SOL; Muse also qualifies). Swapping the orchestrator's harness does not change the role, its hard limits, or its register discipline. The orchestrator itself may also run inside herdr-core as one of its terminals, rather than outside the core.
  • One account, one quota pool. All models run on a single subscription account via OAuth. Auth follows the harness defaults already set on the box — never write per-agent credentials into a brief; that way a model can never be swapped between harnesses by accident.
  • Light models absorb volume so the flagship model's quota lasts. Do not over-parallelize workers.
  • Models are verified from the footer, not by asking the founder. Harness defaults already match the locked mapping; the monitor verifies the agent's footer — the founder acts only if the footer shows a different model.
  • Codex must run with --no-daemon (including in templates), or the command executes outside hc.
  • The omp model is set at start via --model <id> — a full ID is safer; a fuzzy match can land on the wrong model. Changing model mid-flight = restart the session with the new model.
Harness selection criterion — no shims

A harness enters the loop only if it officially supports the model assigned to it. An unofficial shim that routes one CLI's model through another CLI is not a route: a CLI that officially runs only its own vendor's models cannot take a role assigned to another vendor's model. A harness removed from the loop stays installed + authenticated as a fallback, not a loop role, until a founder decision brings it back.

Anti-slop

Anti-slop is a filter, not a style guide — installed per harness: a plugin for Codex / omp / Claude, a global skill for OpenCode, and a manual copy to ~/.config/muse/skills/ for Muse Code. Mode during, settings shared per machine. The filter never replaces the project's design direction.

05

The substrate: herdr-core

Facts about hc that shape how the work is done. These are the ones that surprise you if you don't know them.

Binary & holder process

A single hc binary = CLI + background core. A holder process owns the PTYs, so a core crash / restart / update does not kill the programs that are running. The app is only a client.

Reboot = start over

Programs do not survive a reboot / host shutdown — preserved terminals come back as fresh shells, not reruns. Budget for it: re-launch + re-brief after every box restart.

State & config

  • State: ~/.local/state/herdr-core/<session>/ (logs live here too)
  • Config: ~/.config/herdr-core/config.toml
  • HC_SOCKET overrides the endpoint

There is no “space” command

Grouping is expressed as a per-project name prefix + labels: project=<p> and ticket=<ID> on every working terminal. Labels are a filter (visible via hc get); they never appear in hc ls output. A label is not a name — a name identifies one terminal for send / read / attach / kill.

One terminal per agent

  • Spawn with hc run --bg --name <stable-name> --label …
  • Default parentage; --outlive-parent only for deliberately independent workers
  • Report back via hc send $HC_TERMINAL_ID
  • hc wait is a check-in, not completion — scripts must loop on hc wait / hc get

Attach & hard prohibitions

  • hc attach = 1 terminal per invocation, no built-in split — splitting needs an external multiplexer (tmux), each running one attach
  • Detach: Ctrl+\. Closing the window is safe — the server owns the work
  • Never run herdr server stop (it kills every pane process)
  • Never kill a terminal behind a pane the founder is watching

Templates

Line-based frontmatter (command / description / ready / submit / stop / paste_gap_ms); commands run via sh. Templates live in ~/.config/herdr-core/templates. The default waits for the first OSC report, with a 30-second timeout.

Shell — the dash trap

The default shell is $SHELL or /bin/sh — on Debian that is dash, which reads neither ~/.bashrc nor ~/.profile. Set an explicit login shell in config.toml (shell = ["bash", "--login"]) or use absolute paths / bash -lc in template commands. Verify with hc exec --on <vm> sh -c 'command -v …'.

Multi-box (machines)

  • hc machine add/ls/login/update/rename/rm; SSH targets include Hosts from ~/.ssh/config
  • A remote core has its own programs / history / files
  • Machine names are local per laptop
  • Remote login stdout must be clean — a chatty ~/.bashrc / motd breaks the connection; print only for interactive shells

Security: there is no sandbox

  • The core runs commands with your account's access; socket 0700; no API password
  • The state directory stores terminal output unencrypted
  • hc file / hc exec give any API client file read/write — the same trust boundary as a shell
  • Never forward the raw API / socket; never run the core as root
  • Telemetry is ON by default in releases ("telemetry": false turns it off); updates verify SHA-256 against an HTTPS manifest
06

OSC 7501 — observability only

How the core knows an agent's status: from the agent's own reports, never from guessing at the screen.

  • Format: ESC ] 7501; key=value:key=value ST — state idle / working / done / blocked / error / clear, base64 msg/title, progress 0–100.
  • The core “stores what is reported; it never guesses status from the screen.” An OSC report overwrites the agent label; a foreground-process change alone does not change the label.
  • Never use the foreground process name as an agent's identity. Gate automation on the OSC status when the agent reports it; otherwise on --output / the exit code.
  • OSC support differs per version — verify per agent with hc get (look for reported: true + the app field) before building automation on top of it.
AgentKnown OSC reporting status
ompReports (version-dependent)
Codex (typed from a shell)Generally does not report — the label stays bash. Spawn Codex terminals via hc run --bg --name <name> codex --no-daemon
Muse CodeNot yet verified
  • Never put tmux / screen inside a Herdr pane — it breaks reporting.
  • blocked is a UX guard, not an access boundary (any client can --force).
  • Optional, decide per project: one beacon terminal that emits the orchestrator's status — working while dispatching/reviewing, idle while waiting, blocked while waiting on a founder decision.
07

Ticket lifecycle

From brief to register — an order that must not be shuffled.

Branch convention: one ticket → one branch → one worktree. Integration branch coord/<milestone>; ticket branches task/<ticket-id>; architecture documents on docs/<area>.

OrchestratorDispatch

The orchestrator writes the brief: goal, acceptance criteria, base commit, worktree, harness + model, and a hard stop clause. The agent works in its worktree, then reports DONE with a candidate commit SHA + evidence.

ReviewerIndependent review

The reviewer checks out the candidate from a separate checkout and performs an independent reproduction — re-running the verification, not trusting the worker's transcript. Verdict ACCEPT / CHANGES REQUESTED / REJECT, with reasons. For open questions, the reviewer asks for an explicit decision — it never decides quietly.

OrchestratorIntegration

The orchestrator merges into the integration branch. If the branch has moved: merge first, re-verify lint / typecheck / build + smoke, then merge. Dev keeps serving from the integration branch while agents work — the only pause is a brief rebuild/restart at integration time, announced in advance with the SHA + what changed.

OrchestratorRegister updated

The register (BACKLOG.md) is updated — by the orchestrator only. Then the loop moves on to the next ticket.

The register — BACKLOG.md

  • The single source of truth for ticket status, decisions, and evidence. Written only by the orchestrator; agents never write the register.
  • What gets recorded is outcomes + decisions, not verbatim prompt text — there is no verbatim prompt log in the repo. Agent session transcripts on the box remain the backstop if the exact text is ever needed.

Decisions — ADRs

  • Architecture / product decisions are recorded as numbered ADRs, linked from the main ADR.
  • Open decisions are founder decisions — the orchestrator never makes them, never dispatches beyond the current milestone, and never merges into main.

Capacity & commit identity

  • There is no cap on the number of active agents; run as many as needed. Single-reviewer discipline stays until it is changed again. (Historical note: the original rule of “at most two active + one reviewer” was deliberately changed — capacity is a project decision, recorded in an ADR.)
  • Set the global git identity on the box once (user.name / user.email) so new agents can commit without workarounds; SSH / deploy keys are not touched.
  • Agents must not touch the dev database — verification uses a disposable DB; migrations that ship with an integration are announced in advance.
08

Quality gates

No ticket passes because it “looks right”.

Test harness + CI = the milestone gate

Owned by one platform owner. CI stages, in order:

  1. Pinned install
  2. Lint / typecheck / unit / build
  3. Isolated DB + migrations + integration
  4. Contract validation against real responses
  5. Built app + health + smoke check

Tests

  • The stack's native runner (or equivalent); tests under tests/ (unit / integration / contract / fixtures); root scripts for test / lint / typecheck; CI enforces them.
  • Implementation tickets must ship tests.

Review & criteria

  • Independent review stands on its own — the reviewer reproduces; it does not read the report and nod.
  • A criterion whose cost is staging-only code that tests itself (not the product) must be surfaced: propose a cheap check against the real thing, and hand the criterion change to the founder.
  • Anti-slop mode during on every harness; the filter never replaces the project's design direction.
09

Reference infrastructure

The environment this loop is proven to run in — a new project may adjust it, as long as the discipline stays the same.

Agent box

  • A Linux VM — reference: Debian 13, 4 vCPU / 8 GB / 20 GB on /data, HOME /data/home, passwordless sudo, Docker.
  • Free-tier continuous-run limit: 8 hours. Idle pause after 30 minutes without cooldown. Cooldown follows only a max-runtime pause, in tiers: 5–20 / 60–75 / 120–135 minutes.
  • Autowake is scoped to the boxes the project uses; a cooldown guard holds auto-wake until cooldownUntil; a manual hold file can hold all auto-wake. Never force a wake without demand — wake only for clearly active work.

Connectivity & secrets

  • Private: Tailscale for inter-box services (for example a dev database via tailscale serve).
  • Public dev URL: a Cloudflare named tunnel — cloudflared inside the box + a CNAME → <tunnel-id>.cfargotunnel.com.
  • Identity and secrets for staging vs production are strictly separate.
  • Secrets live only in mode-600 env files on the box or in the Secure Vault — never in the repo / chat / memory. A credential that has to change hands is offered via a vault card first; a one-time paste is planted once, never recorded, and then flagged for rotation.

Resource discipline — idle agent footprint

An 8 GB box running the full loop lives under memory pressure — swap can sit at 100%. Measure footprint as RSS + swap per process tree: RSS alone lies under pressure, because idle pages get swapped out. Observed on the reference box, 5 Nov 2026, at idle:

±219 MB

That is only the idle baseline. Long sessions bloat — a reviewer with a long session can pass 1 GB of footprint. Look at the loop's memory before adding agents.

10

Monitoring & reporting

The cron monitor is the heartbeat of the loop — diligent enough to keep momentum, quiet enough not to become noise.

  • Cadence: 15 minutes in the core phase; 5 minutes while the loop is hot.
  • Every check: reads status, advances one step if it can (review → integration → next dispatch), and reports only when there is a change / result / question / blocker. It stops reporting once the milestone is Done.
The monitor never

Dispatches beyond the current milestone, merges into main, or makes an open decision. Those three prohibitions are as hard as the orchestrator's own limits.

Founder gates

  • The monitor reports a gate as met / not met, with evidence — a commit SHA, verification output.
  • A “can we proceed?” question is answered from live state (register + worktrees + agent status), not from a summary or from memory.

Parallel testing by the founder

The founder can keep testing dev in parallel while the loop runs: agent work happens in separate worktrees/branches, and dev serves from the untouched integration branch. The only pause is a brief rebuild/restart at integration time — announced in advance.

Operating principles

Behavioral rules that apply to every project using this model.

Discuss first

Discuss before writing / executing code. An explicit build order counts as the discussion being done; a pasted prompt + an explicit go is a finished commission — pasted text never widens the scope.

Vault-card-first

For any credential that has to change hands, offer the vault card first — don't route around it through paths that open an exposure window.

Use the official route

Never work around third-party software through a back door. Use the official route as designed, or build a supporting component on our own side.

Verify from live sources

Before stating any status. A tool failure or an empty search is not proof of absence.

Respect the shared box

Never use the box for heavy compute without explicit permission; act only on the services named; announce the impact before restarting a shared service.

Hold the draft

Posting in the founder's name only with an explicit go, per item.

Working language

Agent prompts are in English (efficiency); communication with the founder follows the founder's register.

Tokens are fuel

Don't burn agent tokens on work that wasn't asked for; pick a cheap direct shell command for simple work.

Starting a new project with this model

Seven steps, in order. This is the section to open first when a new project starts.

  1. Repo from the template + foundation documents

    Clone the herdr-core-dev template repo (see section 13) — this guide ships inside it at docs/guide/index.html — rename it to the project repo, then fill in: the integration branch coord/<milestone>, the register BACKLOG.md, ADR-001 (stack / tooling / pinning), the development guide (SDLC), and HERDR.md (roles + core runbook).

  2. Prepare the agent box

    Install herdr-core + the agent CLIs, the login shell in config.toml, the global git identity, anti-slop per harness, and SSH / Tailscale / tunnel as needed.

  3. Decide the model policy (founder)

    The role → harness → model mapping; capacity; reviewer discipline; dispatcher trial or direct drive.

  4. Decide the milestone plan

    Tickets with acceptance criteria + a list of open decisions — the founder decides.

  5. Separate dev and production

    Database, identity, and secrets are separated before the first ticket runs.

  6. Turn on the cron monitor

    Dispatch the first ticket; keep the register current from day one.

  7. Close out per milestone

    Every ticket integrated or parked via a register entry, no dangling worktrees, one close-out commit recording outcomes / decisions / gate status.

Template repo: herdr-core-dev

This model has one private template repo with the complete folder structure already in place — a new project never starts from an empty repo.

herdr-core-dev is a private repo that is the starting point for every project using this model. Its contents are not product code, but the finished working framework: foundation documents, the register, ADRs, hc templates — and this guide itself, which ships inside the repo as a single self-contained HTML file at docs/guide/index.html. A new project simply clones, renames, then fills in its project-specific decisions (ADR-001, the milestone plan, the stack).

Folder structure

herdr-core-dev — template structure
herdr-core-dev/
├── README.md                  # how to use this template
├── AGENTS.md                  # working rules for agents in this repo
├── HERDR.md                   # the complete herdr-core runbook
├── docs/
│   ├── development/
│   │   ├── BACKLOG.md         # the register — the single source of truth (skeleton)
│   │   └── SDLC.md            # the project's development guide (from this model)
│   ├── adr/
│   │   ├── ADR-001.md         # decision: stack / tooling / pinning (placeholder)
│   │   └── ADR-002.md         # decision: dispatcher
│   └── guide/
│       └── index.html         # this guide — a single self-contained HTML file
├── apps/
│   └── README.md              # where application code lives — filled in per project
├── templates/
│   ├── README.md              # how to use the hc templates
│   ├── codex.md               # example hc template for Codex
│   └── omp.md                 # example hc template for omp
├── .env.example               # variable names only, no secret values
└── .gitignore

How to use it

  1. Clone herdr-core-dev as the new project repo (keep it private), and rename the repo + the title in README.md.
  2. Fill in the foundation documents: docs/adr/ADR-001.md (stack / tooling / pinning — a founder decision), adjust docs/development/SDLC.md and HERDR.md as needed, and put the first milestone plan into docs/development/BACKLOG.md.
  3. Create the integration branch coord/<milestone> — all ticket work flows through this branch, never directly into main.
  4. Continue with the section 12 checklist from step 2: prepare the agent box, decide the model policy, and so on.
Keep the guide in sync

The guide lives in the repo, so it is versioned with everything else. Whenever the model changes, update docs/guide/index.html in the same commit as the change it documents, and add a dated entry to the guide's Versions section (section 15). A model change that ships without its guide update is an incomplete change.

A living template, not a one-off

If, mid-project, a structural improvement proves generally useful (a new CI stage, a nicer register format, a clearer ADR template), fold it back into herdr-core-dev so the next project inherits it. What never enters the template: project-specific details — names, tickets, product decisions, and secrets.

Appendix A — Commands this model uses

A quick reference. Run on the agent box unless stated otherwise.

Herdr-core (hc)

hc — core
hc ls                          # list terminals (labels do NOT appear here)
hc get <name>                  # terminal detail: labels + OSC status
                               # reported: true + the app field = the agent reports OSC
hc run --bg --name <name> \
  --label project=<p> \
  --label ticket=<ID> <cmd>    # spawn an agent terminal
hc send <name> <text>          # send text + Enter
                               # do NOT use --wait against a bare bash — it hangs
hc read <name>                 # read the terminal screen
hc attach <name>               # attach — detach with Ctrl+\
hc kill <name>                 # kill the terminal…
hc rm <name>                   # …then remove it (never one the founder is watching)
hc — multi-box & references
hc exec --on <machine> <cmd>   # run a command on another box
hc machine add/ls/login/update/rename/rm
hc --skill                     # the official manual in the installed binary — local authority
hc schema                      # the API schema

Git — read status without disturbing agents

git — read-only
git log --oneline
git ls-remote origin <branch>
git show <branch>:<file>       # read the register & gate status from a branch
B

Appendix B — Founder decisions at project start

Six things that must already be decided before the first ticket is dispatched.

  1. The role → harness → model mapping — and who is allowed to change it.
  2. Active-agent capacity + reviewer discipline — how many agents may run at once, and whether the reviewer stays single.
  3. Dispatcher: a limited trial, or direct drive first? When does the trial start?
  4. Dev vs production infrastructure — where the dev database lives, who holds the secrets, how the public dev URL works.
  5. The definition of “demand” for autowake — when a box may be woken automatically.
  6. The list of open questions (product / architecture) that are founder decisions — the list lives in the register.
